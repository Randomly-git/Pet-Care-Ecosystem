# ActivityRecord 冷热分离实现情况文档

> 本文档详细说明 ActivityRecord（活动记录）的冷热分离实现方案。

---

## 1. 概述

ActivityRecord 冷热分离采用**分离存储**方案：
- 热数据保留在 MySQL（近期数据）
- 冷数据存储到 HBase（历史数据）
- 查询时自动合并，对前端透明

### 1.1 数据流向

```
┌─────────────┐     定期迁移任务      ┌─────────────┐
│   MySQL     │ ──────────────────▶  │   HBase     │
│  (热数据)    │                     │  (冷数据)    │
│  近期记录    │                     │  历史记录    │
└─────────────┘                     └─────────────┘
       ▲                                   │
       │           查询时自动合并            │
       └───────────────────────────────────┘
```

---

## 2. 存储设计

### 2.1 HBase 表结构

**表名**：`petcare_activity_records_archive`

**RowKey 设计**：
```
格式: {pet_id(15位)}_{date(yyyyMMdd)}_{activity_record_id(15位)}
示例: 000000000000004_20250115_000000000000021
```

**列族 `d`**：

| 列名 | 类型 | 说明 |
|------|------|------|
| record_id | Long | 活动记录 ID |
| activity_id | Long | 活动 ID |
| pet_id | Long | 宠物 ID |
| desc | String | 活动描述 |
| date | String | 活动日期（yyyyMMdd） |

### 2.2 设计特点

- **仅存储核心字段**：ActivityRecord 表中只有 5 个字段需要归档
- **不包含关联数据**：Activity、Pet、MediaFile 等关联信息在查询时从 MySQL 补全
- **关联信息实时查询**：冷数据查询时会补全 activityName、activityKindName、petName 等

## 3. 迁移规则与流程

### 3.1 迁移规则

| 条件 | 说明 |
|------|------|
| 创建时间 | 超过 30 天 |
| 访问时间 | 7 天无访问 |
| 状态 | 非 MIGRATING |

### 3.2 迁移流程

```
┌─────────────────────────────────────────────────────────────────┐
│                    定时任务 (每天凌晨执行)                         │
└─────────────────────────────────────────────────────────────────┘
                                │
                                ▼
┌─────────────────────────────────────────────────────────────────┐
│  1. 查询待迁移数据                                                │
│     - 状态为 NONE                                                │
│     - 创建时间 > 30 天                                            │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
                                │
                                ▼
┌─────────────────────────────────────────────────────────────────┐
│  2. 设置 MIGRATING 状态（分布式锁，防止并发迁移）                     │
└─────────────────────────────────────────────────────────────────┘
                                │
                                ▼
┌─────────────────────────────────────────────────────────────────┐
│  3. 查询关联的媒体文件（MediaFile）                                 │
│     - 注意：媒体文件不迁移，只记录关联信息                            │
└─────────────────────────────────────────────────────────────────┘
                                │
                                ▼
┌─────────────────────────────────────────────────────────────────┐
│  4. 写入 HBase（幂等检查）                                         │
│     - 检查数据是否已存在                                           │
│     - 存在则跳过                                                   │
└─────────────────────────────────────────────────────────────────┘
                                │
                                ▼
┌─────────────────────────────────────────────────────────────────┐
│  5. 发送 MQ 事件（异步删除 MySQL）                                  │
│     - 使用消息队列确保可靠性                                        │
│     - Consumer 消费后删除 MySQL 数据                               │
└─────────────────────────────────────────────────────────────────┘
                                │
                                ▼
┌─────────────────────────────────────────────────────────────────┐
│  6. 完成                                                          │
└─────────────────────────────────────────────────────────────────┘
```

### 3.3 是否使用 MQ

**是**，使用 RabbitMQ 进行异步删除：
- **目的**：解耦，提高系统响应速度
- **事件类型**：`MIGRATE_TO_COLD`
- **消费后**：删除 MySQL 中的 ActivityRecord
- **幂等性**：消费前检查数据是否还存在

---

## 4. 幂等性保证

### 4.1 迁移过程幂等性

| 场景 | 处理方式 |
|------|----------|
| 重复迁移同一记录 | HBase exists() 检查，已存在则跳过 |
| 迁移失败 | MIGRATING 状态遗留，下次定时任务继续处理 |
| MQ 重复消费 | Consumer 检查记录是否存在 |

### 4.2 数据一致性保证

```
核心原则：先写后删（Write-Before-Delete）

1. 先将数据写入 HBase
2. 验证写入成功
3. 再删除 MySQL 数据

如果 HBase 写入失败：
  → 不删除 MySQL 数据
  → 下次定时任务重试

如果 MQ 消费失败：
  → 消息会重新投递给 Consumer
  → 最终一致性得到保证
```

## 5. 恢复规则与流程

### 5.1 恢复触发场景

| 场景 | 说明 |
|------|------|
| 用户查看冷数据详情 | 前端请求 → 发现是冷数据 → 触发恢复 |
| 分页查询补充 | 热数据不足 pageSize 时从 HBase 补充 |

### 5.2 恢复流程

```
┌─────────────────────────────────────────────────────────────────┐
│  1. 查询 MySQL 热数据                                             │
│     - 如果存在，直接返回                                          │
└─────────────────────────────────────────────────────────────────┘
                                │
                                ▼ (不存在)
┌─────────────────────────────────────────────────────────────────┐
│  2. 查询 HBase 冷数据                                             │
│     - 按 petId + dateRange 扫描                                  │
└─────────────────────────────────────────────────────────────────┘
                                │
                                ▼
┌─────────────────────────────────────────────────────────────────┐
│  3. 补全关联信息                                                  │
│     - Activity、Pet、ActivityKind 从 MySQL 查询                   │
│     - 媒体文件信息从 COS 补全                                     │
└─────────────────────────────────────────────────────────────────┘
                                │
                                ▼
┌─────────────────────────────────────────────────────────────────┐
│  4. 返回合并结果                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 5.3 恢复是否使用 MQ

**否**，恢复操作是同步的：
- 直接查询 HBase
- 实时补全关联信息
- 返回给前端

## 6. API 说明

### 6.1 对前端完全透明

前端使用现有的分页查询接口，系统自动处理冷热合并：

```
GET /api/activities/records/pet/{petId}
```

**参数**：
| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| petId | Long | 是 | 宠物 ID |
| page | Integer | 否 | 页码，默认 0 |
| size | Integer | 否 | 每页大小，默认 100 |
| startDate | String | 否 | 起始日期（yyyy-MM-dd HH:mm:ss） |
| endDate | String | 否 | 结束日期（yyyy-MM-dd HH:mm:ss） |

**响应**：
```json
{
  "content": [
    {
      "activityRecordId": 123,
      "activityId": 1,
      "activityName": "吃饭",
      "activityKindId": 1,
      "activityKindName": "日常",
      "petId": 4,
      "petName": "旺财",
      "activityDescription": "吃了狗粮",
      "activityDate": "2026-03-28T10:30:00",
      "mediaFiles": []
    }
  ],
  "totalElements": 150,
  "totalPages": 2,
  "size": 100,
  "number": 0
}
```

### 6.2 专用测试接口（仅供测试）

```
GET /api/activities/cold-storage/query
```

此接口用于验证冷数据查询功能，**前端一般不需要调用**。

## 7. 与 Moment 冷热分离的对比

| 特性 | ActivityRecord | Moment |
|------|---------------|--------|
| 存储方式 | 分离存储 | 扁平化单表存储 |
| 关联数据 | 查询时实时补全 | 归档时合并存储 |
| 评论/点赞 | 不涉及 | 归档到 full_data 列 |
| GZIP 压缩 | 无 | 有（full_data 列） |
| 恢复方式 | 直接查询 HBase | 发送 MQ 异步恢复 |
| 恢复耗时 | 毫秒级 | 秒级（MQ + 批量写入） |
| 前端透明性 | 完全透明 | 需要用户操作激活 |

### 7.1 设计选择原因

**ActivityRecord 选择分离存储的原因**：
1. 数据结构简单，仅 5 个核心字段
2. 关联信息变更频繁（如 Pet 名称可能变化）
3. 查询时需要最新关联数据
4. 恢复是读操作，可以同步完成

**Moment 选择扁平化存储的原因**：
1. 关联数据量大（评论、点赞可能很多）
2. 历史数据变更少
3. 减少 HBase 查询次数
4. 恢复后需要批量写入，通过 MQ 解耦
