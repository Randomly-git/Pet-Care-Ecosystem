# ActivityRecord 冷热分离实现情况文档

> 本文档详细说明 ActivityRecord（活动记录）的冷热分离实现方案。

---

## 1. 概述

ActivityRecord 冷热分离采用**分离存储**方案：
- 热数据保留在 MySQL（近期数据）
- 冷数据存储到 HBase（历史数据）
- 查询时自动合并，对前端透明

### 1.1 数据流向

```
┌─────────────┐     定期迁移任务      ┌─────────────┐
│   MySQL     │ ──────────────────▶  │   HBase     │
│  (热数据)    │                     │  (冷数据)    │
│  近期记录    │                     │  历史记录    │
└─────────────┘                     └─────────────┘
       ▲                                   │
       │           查询时自动合并            │
       └───────────────────────────────────┘
```

## 2. 存储设计

### 2.1 HBase 表结构

**表名**：`petcare_activity_records_archive`

**RowKey 设计**：
```
格式: {pet_id(15位)}_{date(yyyyMMdd)}_{activity_record_id(15位)}
示例: 000000000000004_20250115_000000000000021
```

**列族 `d`**：

| 列名 | 类型 | 说明 |
|------|------|------|
| record_id | Long | 活动记录 ID |
| activity_id | Long | 活动 ID |
| pet_id | Long | 宠物 ID |
| desc | String | 活动描述 |
| date | String | 活动日期时间（yyyyMMddHHmm，保留小时分钟） |

**注意**：
- RowKey 中的日期只用于分区和范围查询（yyyyMMdd），不含时间部分
- 列 `date` 存储完整时间信息（yyyyMMddHHmm），保留小时和分钟

### 2.2 设计特点

- **仅存储核心字段**：ActivityRecord 表中只有 5 个字段需要归档
- **不包含关联数据**：Activity、Pet、MediaFile 等关联信息在查询时从 MySQL 补全
- **关联信息实时查询**：冷数据查询时会补全 activityName、activityKindName、petName 等

## 3. 迁移规则与流程

### 3.1 迁移规则

| 条件 | 说明 |
|------|------|
| 创建时间 | 超过 30 天 |
| 状态 | 非 MIGRATING（使用乐观锁） |

**注意**：
1. 简化后的设计不再需要 `last_access_time`，直接根据 `activityDate` 判断
2. 使用乐观锁保证并发安全

### 3.2 迁移流程

```
┌─────────────────────────────────────────────────────────────────┐
│                    定时任务 (每天凌晨执行)                         │
└─────────────────────────────────────────────────────────────────┘
                                │
                                ▼
┌─────────────────────────────────────────────────────────────────┐
│  1. 查询待迁移数据                                                │
│     - 状态为 NONE                                                │
│     - 创建时间 > 30 天                                            │
└─────────────────────────────────────────────────────────────────┘
                                │
                                ▼
┌─────────────────────────────────────────────────────────────────┐
│  2. 【乐观锁】原子性设置 MIGRATING 状态                            │
│     UPDATE activity_record SET migration_status = 'MIGRATING'     │
│     WHERE activity_record_id = ? AND migration_status = 'NONE'   │
│     返回 0 表示已被其他任务锁定，跳过                              │
└─────────────────────────────────────────────────────────────────┘
                                │
                                ▼
┌─────────────────────────────────────────────────────────────────┐
│  3. 发布 MQ 迁移消息（异步）                                       │
│     - 如果发布失败，回滚状态为 NONE                                 │
└─────────────────────────────────────────────────────────────────┘
                                │
                                ▼
┌─────────────────────────────────────────────────────────────────┐
│  4. MQ 消费者处理                                                 │
│     - 检查 HBase 是否已存在（幂等性）                              │
│     - 写入 HBase                                                  │
│     - 删除 MySQL 记录                                             │
└─────────────────────────────────────────────────────────────────┘
                                │
                                ▼
┌─────────────────────────────────────────────────────────────────┐
│  5. 完成                                                          │
└─────────────────────────────────────────────────────────────────┘
```

### 3.3 乐观锁机制

```sql
-- 原子性获取锁（防止并发迁移）
UPDATE activity_record
SET migration_status = 'MIGRATING'
WHERE activity_record_id = :recordId
  AND migration_status = 'NONE';
-- 返回 1 = 获取锁成功
-- 返回 0 = 已被其他任务锁定
```

**好处**：
1. 防止多个定时任务实例重复处理同一记录
2. 即使应用在发布 MQ 消息前崩溃，状态也不会被设置为 MIGRATING
3. 下次扫描时记录仍然可以被正常处理

### 3.4 迁移过程中禁止编辑

**为保证数据一致性，迁移过程中禁止用户编辑/删除记录**：

| 操作 | 限制条件 |
|------|----------|
| 编辑 ActivityRecord | 状态为 MIGRATING 时拒绝 |
| 删除 ActivityRecord | 状态为 MIGRATING 时拒绝 |

**实现方式**：

```java
// ActivityServiceImpl.java
public ActivityRecord updateActivityRecord(Long recordId, ...) {
    ActivityRecord record = activityRecordRepository.findById(recordId)
            .orElseThrow(() -> new RuntimeException("活动记录不存在"));

    // 检查是否正在迁移中
    if ("MIGRATING".equals(record.getMigrationStatus())) {
        throw new RuntimeException("该记录正在迁移中，请稍后重试");
    }
    // ... 继续编辑逻辑
}
```

**好处**：
- 确保用户编辑的是最新数据
- 避免编辑旧数据后数据丢失
- 迁移过程不会被用户操作打断

## 4. 幂等性保证

### 4.1 迁移过程幂等性

| 场景 | 处理方式 |
|------|----------|
| 重复迁移同一记录 | 乐观锁检查：只有状态为 NONE 时才能设置 MIGRATING |
| 迁移失败 | MIGRATING 状态遗留，下次定时任务继续处理 |
| MQ 重复消费 | Consumer 检查 HBase 是否已存在 |

### 4.2 数据一致性保证

```
核心原则：乐观锁 + 先写后删

定时任务阶段：
1. 使用乐观锁原子性设置 MIGRATING 状态
2. 发布 MQ 消息
3. 如果 MQ 发布失败，回滚状态

MQ 消费阶段：
1. 检查 HBase 是否已存在
2. 存在则直接删除 MySQL 记录
3. 不存在则写入 HBase 后删除 MySQL 记录

如果 HBase 写入失败：
  → 消息会重新投递给 Consumer
  → 最终一致性得到保证
```

## 5. 恢复规则与流程

### 5.1 恢复触发场景

| 场景 | 说明 |
|------|------|
| 用户查看冷数据详情 | 前端请求 → 发现是冷数据 → 触发恢复 |
| 分页查询补充 | 热数据不足 pageSize 时从 HBase 补充 |

### 5.2 恢复流程

```
┌─────────────────────────────────────────────────────────────────┐
│  1. 查询 MySQL 热数据                                             │
│     - 如果存在，直接返回                                          │
└─────────────────────────────────────────────────────────────────┘
                                │
                                ▼ (不存在)
┌─────────────────────────────────────────────────────────────────┐
│  2. 查询 HBase 冷数据                                             │
│     - 按 petId + dateRange 扫描                                  │
└─────────────────────────────────────────────────────────────────┘
                                │
                                ▼
┌─────────────────────────────────────────────────────────────────┐
│  3. 补全关联信息                                                  │
│     - Activity、Pet、ActivityKind 从 MySQL 查询                   │
│     - 媒体文件信息从 COS 补全                                     │
└─────────────────────────────────────────────────────────────────┘
                                │
                                ▼
┌─────────────────────────────────────────────────────────────────┐
│  4. 返回合并结果                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 5.3 恢复是否使用 MQ

**否**，恢复操作是同步的：
- 直接查询 HBase
- 实时补全关联信息
- 返回给前端

## 7. 与 Moment 冷热分离的对比

| 特性 | ActivityRecord | Moment |
|------|---------------|--------|
| 存储方式 | 分离存储 | 扁平化单表存储 |
| 关联数据 | 查询时实时补全 | 归档时合并存储 |
| 评论/点赞 | 不涉及 | 归档到 full_data 列 |
| GZIP 压缩 | 无 | 有（full_data 列） |
| 恢复方式 | 直接查询 HBase | 发送 MQ 异步恢复 |
| 恢复耗时 | 毫秒级 | 秒级（MQ + 批量写入） |
| 前端透明性 | 完全透明 | 需要用户操作激活 |

### 7.1 设计选择原因

**ActivityRecord 选择分离存储的原因**：
1. 数据结构简单，仅 5 个核心字段
2. 关联信息变更频繁（如 Pet 名称可能变化）
3. 查询时需要最新关联数据
4. 恢复是读操作，可以同步完成

**Moment 选择扁平化存储的原因**：
1. 关联数据量大（评论、点赞可能很多）
2. 历史数据变更少
3. 减少 HBase 查询次数
4. 恢复后需要批量写入，通过 MQ 解耦
