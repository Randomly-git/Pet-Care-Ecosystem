# 性能测试报告

## 1. API 基准测试（每个端点 50 次请求）

| # | 端点 | 平均 (ms) | 最小 (ms) | 最大 (ms) | 状态码分布 | 所属微服务 |
|---|------|-----------|-----------|-----------|-----------|-----------|
| 1 | `GET /api/media/types` | **6.90** | 5.44 | 11.56 | 200=50 | 📁 media-backend |
| 2 | `GET /api/pets/1` | **6.96** | 4.86 | 32.19 | 401=50 | 🐾 petcare-backend |
| 3 | `GET /api/media/1` | **92.17** ⚠️ | 76.02 | 484.39 | 400=50 | 📁 media-backend |
| 4 | `GET /api/media/related/MOMENT/1` | **21.49** | 15.69 | 107.45 | 200=50 | 📁 media-backend |
| 5 | `GET /api/pets/user/2` | **5.95** | 4.49 | 25.95 | 401=50 | 🐾 petcare-backend |
| 6 | `GET /api/media/99999` | **85.40** ⚠️ | 74.89 | 121.70 | 400=50 | 📁 media-backend |

### 基准测试分析

| 结论 | 值 |
|------|-----|
| ✅ 最优 | `GET /api/pets/user/2` — 平均 **5.95ms**（JWT拦截器直接返回401，无需查库） |
| ✅ 极优 | `GET /api/media/types` — 平均 **6.90ms**（纯枚举返回值，无IO） |
| ⚠️ 需关注 | `GET /api/media/1` — 平均 **92.17ms**，最大 **484ms**（查询DB+COS验证，缓存未命中） |
| ⚠️ 需关注 | `GET /api/media/99999` — 平均 **85.40ms**（查库+抛异常，栈填充耗时） |

## 2. 并发压力测试（10 VUs × 20s）

| 参数 | 值 |
|------|-----|
| 并发虚拟用户数 | **10** |
| 持续时间 | **20s** |
| 测试端点 | `GET /api/media/types` |
| **总请求数** | **3,731** |
| 错误数 | **0** ✅ |
| **平均响应时间** | **13.82 ms** |
| **吞吐量** | **186.55 req/s** |

### 并发测试分析

| 结论 | 值 |
|------|-----|
| ✅ 零错误 | 10并发下无任何 5xx/超时错误 |
| ✅ 吞吐量稳定 | **~187 req/s**，按10VU换算每VU约18.7 req/s |
| ✅ 平均仅小幅上升 | 单线程 6.9ms → 10并发 13.82ms（仅2倍，线性扩展良好） |

## 4. 性能优化建议

| 优先级 | 问题 | 建议 |
|--------|------|------|
| 🟡 中 | `GET /api/media/1` 平均92ms、最大484ms | 单条查询慢：添加 `@Cacheable`（已有但未命中），或确认 `cos_api` SDK 连接池配置 |
| 🟢 低 | `GET /api/media/99999` 平均85ms | 不存在的ID抛出异常 → 改为 `Optional` 提前返回，避免栈填充 |
| 🟢 低 | 吞吐量186 req/s | 如需更高吞吐 → 增加 Gateway 线程池 + petcare-backend 连接池大小 |
