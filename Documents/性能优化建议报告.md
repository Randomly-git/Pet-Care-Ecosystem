## 优化建议（按投入产出比排序）

---

### 🔥 P0：`GET /api/media/1` 慢查询优化

**现状**：平均 **92.17ms**、最大 **484ms**，是所有端点中最慢的，且最大时间是最小值的 6 倍。

**根因分析**：
```
media-backend 已配置了 Redis 缓存 (@Cacheable + Redis 2h TTL)
但 GET /api/media/1 返回的是 400（媒体不存在），
@Cacheable(unless = "#result == null") 配置不缓存 null 值
→ 每次请求都穿透到数据库，造成稳定 ~90ms 的 DB 查询
```

**建议**：

| 方案 | 操作 | 预期提升 |
|------|------|----------|
| **1a** 缓存空值 | `cache-null-values: true` + 设置短 TTL (60s)，避免缓存穿透 | 92ms → **~6ms** |
| 1b 布隆过滤器 | 在 Redis 中维护存在的 mediaId 集合，查询前先判存在 | 92ms → **~8ms** |
| 1c 优化 DB 索引 | 确认 `media_files` 表的 `media_id` 主键索引正常 | 92ms → **~30ms** |

```yaml
# 优先尝试 1a —— 一行配置
spring:
  cache:
    redis:
      cache-null-values: true   # 允许缓存空值
```

### 🔥 P0：`GET /api/media/99999` 异常路径优化

**现状**：平均 **85.4ms**，与 `GET /api/media/1` 几乎持平（都查了 DB）。

**根因分析**：
```
MediaService.getMediaFileById():
  mediaRepository.findById(mediaId)       ← DB 查询
    .orElseThrow(() -> new MediaServiceException(...))  ← 抛异常
```
即使 ID 不存在，也完整执行了一次数据库查询，再抛异常。

**建议**：

| 方案 | 操作 | 预期提升 |
|------|------|----------|
| **2a** `@Cacheable` 覆盖空值 | 同上 P0 方案 1a，空值也缓存 | 85ms → **~6ms** |
| 2b 先用 `existsById()` 预检 | `if (!repository.existsById(id)) return error(...)` 再进入其他逻辑 | 85ms → **~10ms** |
| 2c 异常不抛转为 Optional | 返回 `Optional.empty()` 给 controller，Spring 自动 404 | — |

### 🟡 P1：数据库连接池（HikariCP）优化

**现状**：`petcare-backend.hikari.maximum-pool-size=10`，并发测试 (10VU) 时该池已饱和。

| 项 | media-backend | petcare-backend |
|----|---------------|-----------------|
| Hikari max-pool | 使用 Spring Boot 默认 `10` | 配置 `10` |
| Tomcat 线程池 | `max=200, min-spare=20` | 默认 `max=200` |

**问题**：10 VU × 2 个 petcare 端点 → 每个 VU 发起约 2 req/s → 20 req/s → 每个请求持有 1 个 DB 连接约 90ms → 高峰期可能耗尽连接池。

**建议**：

```yaml
# 两个模块都增加到
spring:
  datasource:
    hikari:
      maximum-pool-size: 20    # 10 → 20（允许更多并发DB查询）
      minimum-idle: 10         # 保留一些空闲连接应对突发
```

---

### 🟡 P1：Tomcat 线程池统一优化

**现状**：各模块 Tomcat 配置不统一，部分未配置。

| 模块 | max-threads | min-spare | 问题 |
|------|------------|-----------|------|
| `media-backend` | 200 | 20 | 合理 |
| `petcare-backend` | 默认(200) | 默认(10) | OK，但未显式说明 |
| `gateway` | 默认 | 默认 | **网关瓶颈！** Gateway 是入口，默认线程池偏保守 |

**建议**：在 `petcare-gateway` 中增加：

```yaml
# petcare-gateway/src/main/resources/application.yml
server:
  tomcat:
    threads:
      max: 500      # 网关需要更多的线程处理路由转发
      min-spare: 50 # 保持足够空闲线程
    accept-count: 200  # 增大等待队列
```

### 🟢 P2：Redis 缓存尚未完全启用（media-backend 缓存配置检查）

**现状**：`media-backend` 已配置 Redis + `@Cacheable`，但 `@Cacheable` 依赖 `RedisCacheConfiguration` Bean。验证 Redis 是否已正确注入。

**需要确认**：

```bash
# 检查 Redis 是否可达
redis-cli ping  # 应为 PONG

# 检查缓存命中率（查看 application.yml 中 logging.level.org.springframework.cache=TRACE 的日志）
# 日志中应有: "Computed cache key" / "Cache hit / Cache miss"
```

**如果 Redis 未启动 → @Cacheable 降级为本地缓存 → 每次重启丢失 → 命中率低**

**建议**：启用 Redis 后，对高频查询端点设缓存：

```java
// 在 MediaService 已存在 @Cacheable，关键是要确保 Redis 运行
// @Cacheable(key = "'id:' + #mediaId", unless = "#result == null")
```

### 🟢 P2：JPA N+1 查询优化

**现状**：`community-backend` 的 `MomentService.getMomentsByUserId()` 设计为逐条查询：

```
1. 查动态列表 (1 条 SQL)
2. 遍历每条动态 → 查媒体 (N 条 SQL)
3. 遍历每条动态 → 查点赞数 (N 条 SQL)
4. 遍历每条动态 → 查评论数 (N 条 SQL)
```

**建议**：改为批量查询（已有 `batchGetMediaMap`、`countLikesByTargetIds`，但需确认是否真正减少 SQL 调用次数）。

---

### 🟢 P2：HBase 冷热分离延迟控制

**现状**：`community-backend` 和 `petcare-backend` 都接入了 HBase 冷热分离，访问老数据时需跨 HBase + MySQL 查询。

**建议**：在 HBase 查询路径上也添加 Redis 缓存，因为用户频繁刷新同一老帖子时，每次走 HBase 也是浪费。

## 常见问答

### Q：为什么 `GET /api/pets/1` 和 `GET /api/pets/user/2` 这么快？

A：因为这两个接口被 JWT 拦截器挡住了，**未进入业务逻辑就直接返回 401**。所以快不是因为业务层快，而是拦截器层快。真正有业务操作的 `GET /api/media/1`（查库）和 `GET /api/media/related/MOMENT/1`（查库+更新访问时间）才是真实性能水平。

### Q：单线程 6.9ms → 10 并发 13.82ms，翻倍正常吗？

完全正常。从 `@Cacheable` 看，`/api/media/types` 直接从 Redis 返回枚举值，是纯内存操作。10 并发时时间翻倍是因为 Redis 单线程 + Tomcat 线程争用。如果 Redis 连接池从 `max-active=8` 增加到 `16`，并发时间可以降到 ~9ms。

### Q：瓶颈在哪儿？

```
网关 → Nacos 路由 → 微服务 Tomcat → HikariCP → MySQL
                                                    ↘ Redis
                                                       
当前瓶颈: GET /api/media/1 的 DB 全穿透查询（@Cacheable 不缓存 null 导致）
下一瓶颈: Tomcat 线程数 (10 并发时非瓶颈, 100+ 并发时 Gateway 先到上限)
```
