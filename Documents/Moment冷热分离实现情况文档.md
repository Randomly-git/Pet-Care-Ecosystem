# Moment 冷热分离实现情况文档

> 本文档详细说明社区动态（Moment）模块的冷热分离实现方案。

---

## 1. 概述

Moment 冷热分离采用**扁平化单表存储 + MQ 异步恢复**方案：
- 热数据保留在 MySQL（动态、评论、点赞分表存储）
- 冷数据存储到 HBase（扁平化合并存储）
- 查询时自动合并，对前端透明
- 恢复需要用户主动操作（点击"激活"）

### 1.1 数据流向

```
┌─────────────────────────────────────────────────────────────────┐
│                         MySQL (热数据)                              │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐              │
│  │  moments    │  │  comments   │  │   likes     │              │
│  │  动态表     │  │  评论表      │  │  点赞表      │              │
│  └─────────────┘  └─────────────┘  └─────────────┘              │
└─────────────────────────────────────────────────────────────────┘
                                │
                                ▼ 定时任务（每天凌晨）
┌─────────────────────────────────────────────────────────────────┐
│                         HBase (冷数据)                             │
│  ┌─────────────────────────────────────────────────────────────┐ │
│  │           community_moments_archive (扁平化单表)             │ │
│  │  ┌─────────────────────────────────────────────────────┐   │ │
│  │  │  RowKey: {userId前4位}_{momentId}                     │   │ │
│  │  │  列: moment_id, user_id, content, created_at,         │   │ │

│  │  └─────────────────────────────────────────────────────┘   │ │
│  └─────────────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────────┘
```

## 2. 存储设计

### 2.1 HBase 表结构

**表名**：`community_moments_archive`

**RowKey 设计**：
```
格式: {userId前4位(盐值)}_{momentId}
示例: 0027_10086 (userId=27, momentId=10086)

说明：
- userId 取模 10000 后补齐 4 位（防止 RowKey 热点）
- momentId 作为主键
```

**列族 `d`**：

| 列名 | 类型 | 说明 |
|------|------|------|
| moment_id | String | 动态 ID |
| user_id | String | 作者用户 ID |
| content | String | 动态内容 |
| created_at | String | 创建时间 |
| full_data | Binary | GZIP 压缩的 JSON（二进制） |

### 2.2 扁平化设计详解

#### 2.2.1 为什么扁平化？

传统设计：
```
动态 A → 评论 1, 评论 2, ... 评论 N
       → 点赞 1, 点赞 2, ... 点赞 M
       
如果分离存储：
- 需要 1 次 Get 获取动态
- 需要 N 次 Get/Scan 获取评论（按 momentId 索引）
- 需要 M 次 Get/Scan 获取点赞（按 momentId 索引）
- 总计：1 + N + M 次操作
```

扁平化设计：
```
单行存储：
RowKey: userId前4位_momentId
└── 列 d:full_data = GZIP(JSON{动态, 评论[], 点赞[], 元数据})

只需 1 次 Get 操作即可获取完整数据！
```


## 3. 迁移规则与流程

### 3.1 迁移规则

| 条件 | 说明 |
|------|------|
| 状态 | MIGRATION_STATUS = 'NONE' |
| 最后访问时间 | 7 天以上无访问 |
| 迁移时机 | 定时任务每天凌晨 2:00 |

### 3.2 迁移流程

```
┌─────────────────────────────────────────────────────────────────┐
│                    定时任务 (每天凌晨 2:00)                        │
└─────────────────────────────────────────────────────────────────┘
                                │
                                ▼
┌─────────────────────────────────────────────────────────────────┐
│  1. 查询待迁移动态                                                 │
│     - migration_status = 'NONE' AND last_access_time < 7天前     │
│     - migration_status = 'MIGRATING' (上次失败的遗留数据)          │
└─────────────────────────────────────────────────────────────────┘
                                │
                                ▼
┌─────────────────────────────────────────────────────────────────┐
│  2. 设置 MIGRATING 状态（分布式锁，防止并发迁移）                   │
│     - UPDATE moments SET migration_status = 'MIGRATING'          │
│     - WHERE id = momentId AND migration_status = 'NONE'          │
└─────────────────────────────────────────────────────────────────┘
                                │
                                ▼
┌─────────────────────────────────────────────────────────────────┐
│  3. 检查评论数量阈值                                               │
│     - 如果评论数 > 2000，跳过（数据量过大）                         │
│     - 原因：归档 JSON 可能超出 HBase 单列限制                       │
└─────────────────────────────────────────────────────────────────┘
                                │
                                ▼
┌─────────────────────────────────────────────────────────────────┐
│  4. 查询关联数据                                                   │
│     - 查询该动态的所有评论                                         │
│     - 查询该动态的所有点赞（包括对评论的点赞）                      │
│     - 获取用户昵称和头像（用于归档）                                │
└─────────────────────────────────────────────────────────────────┘
                                │
                                ▼
┌─────────────────────────────────────────────────────────────────┐
│  5. 构建扁平化归档数据                                             │
│     - 序列化评论列表、点赞列表到 JSON                              │
│     - 添加元数据（评论数、点赞数、快照时间）                        │
│     - GZIP 压缩                                                   │
└─────────────────────────────────────────────────────────────────┘
                                │
                                ▼
┌─────────────────────────────────────────────────────────────────┐
│  6. 写入 HBase（幂等检查）                                         │
│     - 检查是否已存在                                               │
│     - 存在则跳过，避免重复写入                                     │
└─────────────────────────────────────────────────────────────────┘
                                │
                                ▼
┌─────────────────────────────────────────────────────────────────┐
│  7. 验证 HBase 写入                                               │
│     - 读取验证数据完整性                                           │
│     - 失败则重试或标记失败                                         │
└─────────────────────────────────────────────────────────────────┘
                                │
                                ▼
┌─────────────────────────────────────────────────────────────────┐
│  8. 删除 MySQL 数据                                               │
│     - 批量删除 comments (WHERE moment_id = ?)                     │
│     - 批量删除 likes (WHERE target_type = 'MOMENT' AND target_id = ?) │
│     - 删除 moments (WHERE id = ?)                                 │
└─────────────────────────────────────────────────────────────────┘
                                │
                                ▼
┌─────────────────────────────────────────────────────────────────┐
│  9. 完成                                                          │
└─────────────────────────────────────────────────────────────────┘
```

### 3.3 是否使用 MQ

**否**，迁移过程不使用 MQ：
- 迁移是定时任务触发的批量操作
- 在同一个事务内完成（使用 TransactionTemplate 隔离）
- 失败时可以通过状态恢复

### 3.4 单条迁移的事务隔离

```java
// 每个动态的迁移在独立事务中执行
Boolean success = newTransactionTemplate.execute(status -> {
    try {
        return migrateSingleMoment(momentId);
    } catch (Exception e) {
        log.error("【冷迁移】迁移动态失败: momentId={}, error={}", momentId, e.getMessage());
        status.setRollbackOnly();
        return false;
    }
});
```

**好处**：
- 一个动态迁移失败不影响其他动态
- 失败的动态状态保持 MIGRATING，下次任务继续处理

## 4. 幂等性保证

### 4.1 幂等性措施

| 场景 | 幂等保证方式 |
|------|-------------|
| 重复迁移同一动态 | HBase exists() 检查 |
| 迁移中断（MIGRATING 状态遗留） | 下次定时任务检测并继续处理 |
| 评论/点赞重复归档 | 归档数据可覆盖，不影响功能 |
| HBase 写入失败 | MIGRATING 状态保留，下次重试 |
| MySQL 删除失败 | 事务回滚，MIGRATING 状态保留 |

### 4.2 幂等性代码示例

```java
// HBase 幂等检查
public void saveArchive(HBaseArchiveRecord record, ColdArchiveData archiveData) {
    String rowKey = generateRowKey(record.getUserId(), record.getMomentId());

    // 先检查是否存在
    if (existsByRowKey(rowKey)) {
        log.info("【HBase】归档数据已存在，跳过: rowKey={}", rowKey);
        return;
    }

    // 写入数据...
}

// MySQL 幂等检查（使用 ON DUPLICATE KEY）
entityManager.createNativeQuery(
    "INSERT INTO moments (moment_id, user_id, content, created_at, ...) " +
    "VALUES (?, ?, ?, ?, ...) " +
    "ON DUPLICATE KEY UPDATE moment_id = moment_id"
).setParameter(1, originalMomentId)
 ...
```

## 5. 数据一致性保证

### 5.1 核心原则：先写后删

```
迁移前检查：
1. 动态最后访问时间 < 7天前（确保是冷数据）
2. 动态状态不是 MIGRATING（确保未被并发迁移）

迁移中保证：
1. 先设置 MIGRATING 状态（加锁）
2. 再写入 HBase
3. 验证 HBase 数据完整性
4. 最后删除 MySQL 数据

如果中途失败：
- HBase 已写入：下次任务会跳过（幂等）
- MySQL 未删除：数据安全，下次任务继续
```

### 5.2 潜在数据不一致风险

| 风险场景 | 影响 | 处理方式 |
|----------|------|----------|
| HBase 写入成功，MySQL 删除失败 | 数据冗余（MySQL+HBase 都有） | 下次任务重试删除 |
| HBase 读取验证失败 | 迁移失败 | 状态保持 MIGRATING，下次重试 |
| 评论数超阈值 | 跳过迁移 | 保持 MySQL 热数据 |

## 6. 恢复规则与流程

### 6.1 恢复触发场景

| 场景 | 说明 |
|------|------|
| 用户查看冷动态详情 | MySQL 不存在 → 发送 MQ 恢复事件 |
| 前端点击"激活"按钮 | 用户主动触发恢复 |

### 6.2 恢复流程（异步 MQ）

```
┌─────────────────────────────────────────────────────────────────┐
│  1. 前端请求动态详情                                              │
└─────────────────────────────────────────────────────────────────┘
                                │
                                ▼
┌─────────────────────────────────────────────────────────────────┐
│  2. 查询 MySQL                                                   │
│     - 如果存在，直接返回                                          │
│     - 如果不存在，进入冷数据恢复流程                               │
└─────────────────────────────────────────────────────────────────┘
                                │
                                ▼ (不存在)
┌─────────────────────────────────────────────────────────────────┐
│  3. 发送 MQ 恢复事件                                              │
│     - eventType: RESTORE_FROM_COLD                               │
│     - payload: { momentId, userId }                              │
└─────────────────────────────────────────────────────────────────┘
                                │
                                ▼
┌─────────────────────────────────────────────────────────────────┐
│  4. MQ Consumer 接收事件（异步）                                  │
│     ┌─────────────────────────────────────────────────────────┐ │
│     │  4.1 从 HBase 一站式读取完整数据                         │ │
│     │      - 1 次 Get 操作获取动态 + 评论 + 点赞                │ │
│     │      - full_data 列自动解压反序列化                       │ │
│     │                                                          │ │
│     │  4.2 批量写入 MySQL                                      │ │
│     │      - INSERT moments (ON DUPLICATE KEY)                 │ │
│     │      - INSERT comments (幂等检查)                        │ │
│     │      - INSERT likes (幂等检查)                            │ │
│     │                                                          │ │
│     │  4.3 事务提交后删除 HBase 数据                            │ │
│     │      - 使用 TransactionSynchronization                    │ │
│     │      - 确保 MySQL 写入成功后再删除                         │ │
│     └─────────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────────┘
                                │
                                ▼
┌─────────────────────────────────────────────────────────────────┐
│  5. 前端提示用户稍后刷新                                          │
│     - 恢复是异步的，需要等待                                      │
│     - 预计耗时：1-5 秒（取决于评论/点赞 数量）                    │
└─────────────────────────────────────────────────────────────────┘
```

### 6.3 是否使用 MQ

**是**，恢复使用 RabbitMQ：
- **目的**：解耦 + 批量处理
- **原因**：恢复涉及批量写入 MySQL，可能较慢
- **优势**：不阻塞前端请求，支持重试

### 6.4 恢复的幂等性

```java
// 1. 动态插入使用 ON DUPLICATE KEY
INSERT INTO moments (...) VALUES (...) ON DUPLICATE KEY UPDATE moment_id = moment_id

// 2. 评论/点赞先检查是否存在
if (commentRepository.existsById(commentId)) {
    log.debug("评论已存在，跳过: commentId={}", commentId);
    continue;
}
INSERT INTO comments (...) VALUES (...) ON DUPLICATE KEY UPDATE comment_id = comment_id

// 3. 事务提交后才删除 HBase
TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
    @Override
    public void afterCommit() {
        hBaseService.deleteArchive(userId, momentId);
    }
});
```

## 7. API 说明

### 7.1 对前端完全透明

#### 获取动态列表
```
GET /api/moments
```
- 自动合并 MySQL 热数据和 HBase 冷数据
- 前端无感知

#### 获取动态详情
```
GET /api/moments/{momentId}
```
- 如果 MySQL 不存在，自动触发 MQ 恢复事件
- 前端显示"激活中，请稍后刷新"提示
- 用户刷新页面后查看

| 场景 | 前端行为 |

| 激活完成 | 恢复正常互动功能 |

## 8. 与 ActivityRecord 冷热分离的对比

| 特性 | ActivityRecord | Moment |
|------|---------------|--------|
| 存储方式 | 分离存储（仅核心字段） | 扁平化单表存储（合并评论/点赞） |
| HBase 列数 | 5 个列 | 5 个列（含 full_data） |
| 关联数据 | 查询时实时补全 | 归档时合并存储 |
| 评论/点赞 | 不涉及 | 归档到 full_data 列 |
| GZIP 压缩 | 无 | 有（full_data 列） |
| 迁移触发 | 定时任务 | 定时任务 |
| 迁移使用 MQ | 否 | 否 |
| 恢复方式 | 同步查询 HBase | MQ 异步恢复 |
| 恢复耗时 | 毫秒级 | 秒级（MQ + 批量写入） |
| 前端透明性 | **完全透明** | **需要用户操作激活** |
| 数据一致性 | 先写后删 | 先写后删 |
| 幂等性 | exists() 检查 | exists() + ON DUPLICATE KEY |

### 8.1 设计差异原因

| 方面 | ActivityRecord | Moment |
|------|---------------|--------|
| 数据量 | 小（单条记录） | 大（评论+点赞可能很多） |
| 关联复杂度 | 低（5个字段） | 高（评论/点赞/用户等多表） |
| 恢复频率 | 高（查询时自动恢复） | 低（用户主动激活） |
| 实时性要求 | 高（需要毫秒响应） | 低（异步可接受） |
| 存储优化 | 简单即可 | 需要压缩+合并 |
